# Principles

保留会改变决策的判据。语言细节见 `rust-principles` / `kotlin-principles`，设计审查见 `review`，流程关系见 `flow`。

## 工程取舍

- **Good Taste**：优先通过建模消除特殊情况，避免不断补条件分支。
- **Never Break Consumer**：兼容包括行为、配置、错误、持久化格式和最低工具链。破坏性变化需要明确约定和迁移路径。
- **实用主义**：解决已存在或可验证的问题；复杂度需要有具体收益。
- **简洁**：选择易理解、易验证、易撤销的实现。行数、嵌套和文件数量是观察信号，不是失败线。

比较方案时考虑可测试性、可读性、项目一致性、简洁性和可逆性；按当前风险权衡，不机械排序或制造第二方案。

## 数据、行为与领域归属

默认用 ADT/value type 表达状态和合法组合；需要能力抽象时使用 trait/interface 与解释器。普通领域函数、方法和扩展函数同样可以承载行为，不为每个操作预制接口。

数据与行为可以在表示上分离，但领域规则应有明确归属：

- 类型或受控构造入口维护值的有效性；状态转换明确输入、结果和失败语义。
- 领域模块拥有规则与决策，应用层协调调用和 I/O。规则不因放在成员方法里就自动正确，也不因放在纯函数里就失去封装。
- 不可变值不自动保证不变量或持久化并发一致性；按实际约束限制构造、写入和并发更新。
- 纯规则与运行时状态拥有者分工清楚。有状态 Service 可以存在，但需要明确生命周期和并发访问方式，不能自动变成全局 singleton。

抽象从 consumer 的真实需求中发现。共同签名或实现数量不足以证明共同能力；接口只暴露调用方需要的语义。

## 领域边界与 Bounded Context

Bounded context 是一套业务语言和模型保持一致的适用范围；模块/crate 是代码组织方式。一个上下文可包含多个模块，也不必独立部署。

- **规则所有权**：边界内明确负责哪些业务决策、事实和不变量。按职责组织模块，命名只是线索。
- **局部统一语言**：同一上下文内词义一致；不同上下文的同名概念可以有不同模型，通过明确契约转换。
- **跨边界契约**：依赖公开能力、事件或约定的数据契约，避免读取内部表示、直接改写对方状态，或在调用方重新实现对方规则。
- **共享模型**：字段相似不足以提取 `common`。共享需要共同语义、明确 owner 和演进约定；必要的重复优于错误耦合。
- **变化检验**：一条规则经常迫使多个模块协调修改，是归属错位或内部表示泄漏的信号；合理的跨上下文交付仍可一起实现。
- **一致性**：上下文不等于聚合或事务边界。涉及跨边界写入时说明必须保持的约束、协调责任及失败恢复方式。

先复用项目已有边界与契约。只在新建或调整边界时深入上述问题，不为每个小模块创建完整 DDD 文档。

## 框架与资源边界

- 框架类型停在 adapter；进入核心前转换成领域输入。composition root 负责构造与接线，业务决策留在领域。
- 后台任务、线程、连接和服务有明确 owner、停止路径和失败传播；按用途说明 timeout、等待和清理。
- 使用项目 manifest/lockfile 对应的 API；兼容性和关键行为优先用可执行检查验证。

## AI 协作

- 目标和授权明确时，自主完成必要的可逆工作；按真实依赖读取代码，不把修改范围当成阅读白名单。
- 常规实现选择由 AI 判断并说明依据。关键歧义、未覆盖的重要取舍、真实范围扩张或权限不足时再向用户提问。
- 用户已表达的偏好和授权在适用范围内持续有效，不在每个阶段重新确认，也不扩展到无关任务或未授权的外部动作。
- 验收目标在实现前明确；已有测试、计划和文档足够时直接复用。跨 session 的重要事实和决策落到项目约定的文档。
- 保持一个可 review 的交付，按真实风险补设计、验证与迁移，不用固定流程代替判断。

需要用户选择时给真实选项、trade-off 和推荐；信息确认可以直接问，已有答案不重问。用户要求交互选择时优先使用宿主适合该问题的选择工具，不可用时用文本呈现。
