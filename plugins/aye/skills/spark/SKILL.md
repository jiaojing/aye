# Spark

按用户当前意图保存或探索想法。保存不等于探索，推荐也不等于实施承诺；已有决定和授权按 `flow` 继续承接。

## 保存

用户要求“记一下 / 先存着”时，沿用项目约定，默认追加到 `docs/inbox.md` 的 `## Inbox`：

```markdown
- <一句话想法，保留必要来源或约束> [#optional-tag]
```

保持 raw bullet，不为暂存想法添加 acceptance、task、priority 或 active focus。完成后回到当前请求。

## 探索

用户要求展开、判断价值或可行性时：

- 理解真实问题、约束与现有事实，只询问会改变判断的关键未知项。
- 比较实际存在的产品或流程形态，说明收益、代价、风险和推荐依据；不为凑选项制造方案。
- 记录未确定之处和实际决定；“暂存 / 不做”可以是合理结论，不把推荐写成已承诺的验收与任务。

普通探索直接对话。用户要求 proposal、存档或需要跨 session 复用时，优先更新已有文档；默认新提案为 `docs/sparks/<YYYY-MM-DD>-<slug>.md`。项目已有其他提案位置时沿用，无需迁移旧文档。

提案按需要包含问题与事实、真实候选、推荐依据、未决事项和决定，不要求固定模板或状态字段。来自 inbox 的条目在被承接或用户要求删除前保留。

## 承接与清理

| 用户意图 | 动作 |
|---|---|
| “做这条” | 目标模糊时用 feature 澄清；目标与授权明确时由现有任务直接实施 |
| “删掉这条” | 删除指定想法或提案 |
| “回顾这些完成项” | 依据已完成 feature 汇总事实，保留来源链接 |

想法承接后，先确认下游文档或任务已记录目标，再移除原 inbox 条目，避免丢失来源。探索结论本身不触发移除或实施。

用户请求 retrospective epic 时，沿项目约定记录；默认 `docs/epic-<slug>.md`，索引放在 `docs/inbox.md` 的 `## Epics`。它汇总已完成事实，不根据条目数量自动创建。

保存和探索按请求使用；handoff 负责交接当前工作，不自动触发想法管理。已有 backlog、优先级和项目文档布局继续沿用。
