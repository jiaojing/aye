# Scope Align

在改代码前锁定本次 PR 会改什么、明确不改什么。它防止横向“顺手清理”和纵向“顺便升级需求”。

## 何时必走

任一命中时走完整对齐：

- 改多个文件、公开 API、持久化 schema 或跨模块边界；
- 任务含“整理 / 优化 / 重构”等模糊词；
- 第一次进入陌生模块；
- 已发现可能需要扩大用户原始请求。

typo、单行明确修改、边界显然的单文件任务和纯文档任务可跳过仪式，但仍要遵守既定 scope。

## Scope 提议

```markdown
## Scope 提议

### In
- `<path>`：<本次修改>

### Out
- `<path/方向>`：<为什么本次不动>

### 不确定项
- <只列会改变文件、兼容性或交付内容的真实决策；按 pick 协议呈现>

### 预计改动
<文件数 / 大致量级 / 公开边界>
```

Out 只列真实可能漂移的方向，不为填模板制造 non-goal。

## 确认与实施

- 使用交互式选择工具时，用户完成选择即代表确认这些决策；输出最终 scope 后直接实施。
- 纯文字提议必须等用户明确“OK / 动手 / 调整”。
- 不确定项按 `pick` 协议提供候选、trade-off、推荐和理由。
- 实施中发现必须新增文件或改变边界时立即停下，重新提出 scope；不要静默扩张。

## 下一步

scope 确认后按顺序分流：

1. 命中 acceptance 条件时进入 `acceptance`；
2. acceptance 完成后，若是大功能、多方案、schema 或跨模块设计，再进入 `design`；
3. 其余任务直接实施。

禁止从 scope 直接跳到 design 绕过本应存在的 acceptance。
