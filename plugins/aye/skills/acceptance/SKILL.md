# Acceptance

明确“什么算完成”。实现前确定可观察的结果，验证强度与风险匹配；测试绿不自动证明所有业务行为、兼容性和迁移都完成。

## 验收质量

每条说明具体输入或场景、预期结果、观察方式和通过条件。例如：

```markdown
- [ ] <输入/场景与预期行为> | 验证：<测试、command 或明确操作>
```

复用有效的 AC、失败测试或已有检查，只补本次改动留下的验证缺口。语义不变的小重构和纯文档修改使用相应检查，不为填清单制造新测试。

需要持久化清单时更新现有 feature、issue 或项目约定文档，避免重复维护同一验收目标。

## 按风险补验证

| 改动 | 关注 |
|---|---|
| 领域规则/状态转换 | 合法与非法输入、不变量、状态转换及失败语义 |
| 领域边界/契约转换 | 调用方可观察行为、语义映射、规则归属；必要时检查依赖方向 |
| 跨边界写入 | 一致性约束、并发冲突、部分失败与恢复 |
| 公开 API | consumer、兼容性、deprecation/migration |
| 持久化/config | 旧数据与配置、迁移、回滚 |
| 后台工作/外部 I/O | 取消、timeout、shutdown 和失败传播 |
| CLI/HTTP/GUI adapter | 真实入口与领域核心之间的转换 |
| 并发代码 | 显式同步或虚拟时间，避免用 sleep 猜调度 |
| 不可信输入 | 相关权限、边界与非法输入处理 |

只选择与本次风险有关的项。不能验证的部分明确记录；不要用“应该没问题”充当通过证据。

需要澄清影响完成条件的用户决策时再提问；其余流程关系见 `flow`。
