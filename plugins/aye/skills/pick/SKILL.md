# Pick

把用户下一次需要拍板的决策工具化。只作用于下一次提问，不接管后续节奏。

## 先确认是真决策

- 2–4 个互斥候选，选一个即可推进：使用本协议。
- 开放探索、信息确认、已经表达过偏好的事项：直接对话，不包装成选择题。
- 候选超过 4 个：先按关键维度收敛或拆成多个问题。

## 候选质量

按 `principles` 的决策点规则构造：候选 + trade-off + 推荐 + 理由。推荐项放第一，label 末尾加 ` (Recommended)`。

## 工具呈现

有原生交互式选择工具时优先使用，字段映射如下：

| 字段 | 内容 |
|---|---|
| `header` | 短标题 |
| `question` | 一句话决策点 |
| `options[].label` | 候选短名；推荐项置首 |
| `options[].description` | 主要 trade-off + 推荐理由 |

- Claude Code：使用 `AskUserQuestion`；schema 未加载时先搜索工具。
- Codex：使用当前会话暴露的原生选择工具。
- 无可用工具：使用结构化文本，仍保留候选、trade-off、推荐和理由。

文本 fallback：

```markdown
- A（推荐）：<方案> —— <trade-off>
- B：<方案> —— <trade-off>

推荐 A，因为 <理由>。
```

收到选择后，把结果写回当前 feature/scope/acceptance/design 或对话决策记录，然后回到原流程。

## 禁止

- 裸列编号让用户自己研究差异。
- 候选不互斥或包含组合项。
- 用户已经表态后再重复确认。
- 单次触发后默认所有后续问题都必须工具化。
