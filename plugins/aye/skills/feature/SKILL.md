# Feature

澄清 what / why，为后续实施和接力提供稳定目标。复用已有 feature、issue 和项目文档；明确的 bug fix、小改或已规划任务可以直接实施。

## 内容

先阅读相关代码与文档，区分已知事实、假设和真正需要用户决定的问题。技术细节由 design 承接，不用实现步骤替代用户结果。

需要新文档时默认采用下列形态，已有项目约定优先：

```markdown
# <feature 名>

## Feature
<当前问题、影响与目标>

### Users
<使用或受影响的人>

### Scope
<交付内容，以及真正可能漂移的非目标>

### Constraints
<业务、技术与兼容约束>

### Open questions
<影响目标或验收的真实未知项；没有则省略>

## Acceptance
- [ ] <用户视角可验证的结果>

## Tasks
- [ ] <可独立验收和 review 的交付>

## Notes
<关键事实和决策，链接相关设计>
```

默认位置为 `docs/features/<YYYY-MM>-<kebab-slug>/feature.md`；按需要增加 design/ADR，不预建占位文档。

## 交付粒度

- 按可独立验收、review 和回滚的结果拆分，避免按文件、前后端或技术层机械切任务。
- 同一用户交付可以跨多个领域上下文；分别明确规则 owner 与协作契约。
- 同模板、同验收的机械工作可以合并。task 不绑定 commit 数量。
- 方向仍未定时记录阻塞决策，不虚构完整任务清单；常规实现细节留给实施。

任务状态沿用 `[ ]`、`[>]`、`[x]`；有提交时可记录 `done @ <sha>`，提交/推送状态如实区分。

## 协作

- 已明确的目标、决策和授权直接复用；必要的文档草稿可先写入并标出未决项。
- 只询问会改变交付或验收的关键未知项，常规实现选择自主判断。
- 用户要求只规划、存档或先确认时停在对应阶段；已授权实施且目标足够清楚时继续工作，不为切换 skill 重复确认。

流程分流见 `flow`。
