# Design

在交付目标和验收含义明确后决定技术 how。需要重要决策或跨 session 接力时记录设计；沿既有契约跨模块实现、多文件修改或存在普通实现选项，本身不要求新设计文档。

## 理解现状

检查相关领域的规则归属、公开契约、依赖方向与接线位置，以及真实 consumer、持久化约束和项目版本。优先使用现有能力与模式。

## 收敛与记录

- 说明需要决策的问题、约束、选择与依据；存在真实替代方案时比较收益和代价。
- 常规技术选择自主判断。用户已指定方案或授权必要的可逆实施时，不重复请求批准。
- 目标有关键歧义、重要取舍未被覆盖，或用户要求先讨论时，先给具体可 review 的方案并等待对应决策。
- 复用现有 design/ADR；需新文档时默认 `docs/features/<slug>/design.md`，遵循项目已有位置。草稿可先落盘，明确标出假设和未决项。

模板按实际需要取舍：

```markdown
# Design: <交付>

## 问题与约束
<需要技术决策的原因，链接已有目标与验收>

## 决策
<选择、理由、真实替代方案、假设与未决项>

## 实施
<规则归属、契约、依赖、数据流/状态转换与验证>

## 风险与恢复
<实际风险、迁移或回滚方式>
```

## 条件化设计判据

| 场景 | 需要讲清 |
|---|---|
| 新建/调整领域边界 | 职责、业务语言与规则 owner；公开契约、依赖方向和语义转换 |
| 跨边界写入 | 不变量对应的事务/聚合边界、协调责任、部分失败与恢复 |
| 后台任务/并发 | 状态 owner、启动/取消/等待、timeout 和失败传播 |
| 外部 I/O | timeout、重试与幂等性、错误映射和 shutdown |
| 框架接入 | adapter 与进入核心的领域输入 |
| 重要 API/协议变化 | consumer、兼容策略、验证与迁移 |
| 持久化/schema | 旧数据、migration、回填、回滚 |
| 缓存 | freshness、失效与一致性 |

详细契约或 schema 可拆到 `contracts.md` / `schema.md` 并链接，避免多份文档重复描述同一事实。

设计与验收可以迭代完善；实际实施前解决阻塞决策，已有决策足够时继续工作。流程关系见 `flow`。
