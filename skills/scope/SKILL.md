# Scope Align

AI 协作的**闸门 1**:动手前对齐 scope。

AI 写代码很快,人 review 很慢。**对齐成本一定要前置**——先用 1 分钟对齐 scope,远胜过事后用 30 分钟回滚不该改的代码。

---

## 为什么需要

AI 在两个方向天然容易越界:

1. **横向越界**:给个修 bug,顺手"清理"周边代码;给个加字段,顺手重构相关 service
2. **纵向越界**:任务说"加 logging",AI 自己加成"加 logging + 加 tracing + 加 metrics"

人脑读代码是连贯的,看到不顺眼会停下来纠结;AI 是文档式补全,看到"机会"就顺手做。这不是 AI 的 bug,是 AI 协作的内禀特性。**只能用显式仪式对冲**。

---

## 何时必走 / 何时跳过(硬清单)

**必走**(任一命中):

- 改 ≥ 2 个文件
- 改公开 API / 持久化 schema / 跨 crate 边界
- 任务描述模糊("整理 / 优化 / 重构")
- feature 有多种合理解读
- 陌生模块第一次动
- AI 自己感觉"这块还有顺手能做的"

**跳过**(任一命中即可直接进写代码):

- typo 修复 / 单行明确改动
- 紧急 hotfix
- 单文件 + 任务边界显然(用户已指明改哪个 fn / 哪几行)
- 文档型 task(写 markdown / review.md / SKILL.md)

跳过 ≠ 不对齐——心里仍要清楚"改哪些 / 不改哪些",只是不必走全套仪式。

---

## 触发场景(用户口语)

用户说这些话时,AI 自动 invoke:

- "开始改 / 动手 / 做这条 / 实现一下"
- "改 X / 修一下 / 这个怎么改"
- "准备写代码 / 实施"

但**先看"何时必走 / 跳过"硬清单**——简单 task 即使触发也跳过仪式。

## 仪式三步

### 1. AI 提议 scope

AI 在动手前**先输出一段 scope 提议**,模板:

```markdown
## Scope 提议

### In-scope(本次会改的)
- [文件 A] 加 X 字段
- [文件 B] 改 Y 函数签名,从 (a, b) → (a, b, c)
- [文件 C] 新建,放 Z 工具函数

### Out-of-scope(本次明确不动)
- [文件 D] 注意到 Q 问题,但不在本次修(独立任务)
- 文档同步、CHANGELOG 等留下一轮

### 不确定项(需要用户确认)

每项按 **候选 + trade-off + 推荐 + 理由** 输出(见 `principles` 的「AI 不当提问机」段)。环境支持 `AskUserQuestion` 时优先用工具,用户键盘选。

- Q1: 兼容 legacy P 路径?
  - 候选 A: **兼容**(推荐)—— trade-off: scope +1 文件;迁移期 0 用户感知
  - 候选 B: 不兼容 —— trade-off: 代码干净;~3 处调用方手动迁移
  - **推荐 A**,因为 legacy 还有活用户,先兼容再渐进迁
- Q2: N 处旧调用顺手迁移?(候选 + trade-off + 推荐 同上格式)

### 预计改动量
~3 文件 / ~80 行
```

### 2. 用户答(按提议形式分两条路)

| 路径 | 流程 |
|---|---|
| **AskUserQuestion 提议**(不确定项工具化) | 用户在工具里选完 = **已点头**,AI 输出最终锁定的 scope 清单 + **直接动手**。不要再追问"说'动手'我才开干"——工具答复本身就是动手许可 |
| **纯文字提议**(0 个不确定项 / 工具不可用) | 用户明示"ok / 动手 / 调整 / 重来"才进下一步 |

无论哪条路,用户**任何时刻**可中途打断("等等 别动 D / 多改一个 E")—— AI 不需要每步预防式问。

### 3. 写下 scope + 动手

scope 锁定后,**写在对话里 / 任务列表 / PR 描述**(留 trail),然后开始改代码。

后续如果发现真的需要扩 scope,**停下,回到第 1 步重新提议**,不要"已经动手了顺便就做了"。

## 反例(常见失守模式)

### 反例 1:静默扩 scope

```
用户:"把 createUser 加个 email 校验"
AI:[改了 createUser + 顺手把 createOrg 也加了 + 又改了 validate utils]
30 分钟后用户:"等等,你怎么改了 createOrg?"
```

**对治**:仪式第 1 步逼 AI 显式列出 in-scope,不能"顺手"。

### 反例 2:不确定项自己拍

```
用户:"删掉 legacy auth 路径"
AI:[直接删,但 legacy 还有 N 处调用方]
集成测试挂:"为什么 N 个测试挂了?"
```

**对治**:仪式第 1 步必须列"不确定项",等用户回答。

### 反例 3:对齐过但中途变更不重提

```
对齐:改文件 A、B
中途:AI 发现 C 也需要改,直接改了
用户 review:"C 怎么也动了?"
```

**对治**:scope 是动手前的契约,中途变更要回到第 1 步重提议,不是"既然在改了顺便"。

## 输出格式建议

### 用了 AskUserQuestion(有不确定项)

工具答完 → 直接给"最终锁定 scope"清单 → **立刻动手**。**不要**再追加"说动手我就开干"——重复二次确认是反模式。

```markdown
## 最终 scope 锁定(用户已在工具里答完)
- In-scope:文件 A / 文件 B / ...
- Out-of-scope:...

[开始改代码 / 调用 Edit / Write]
```

### 纯文字提议(0 个 Q / 工具不可用)

scope 提议块末尾保留闸门提示:

```markdown
[scope 提议如上]

---

请 review 后:
- "ok" / "动手" → 开始
- "调整:..." → 改后再确认
- "重来" → 重新提议
```

## 与其他 skill 的关系

- **`flow`**:地图。本 skill 是地图上的**闸门 1**(动手前)。
- **`acceptance`**:scope 对齐**之后**的下一步——钉死 DoD。先 scope 后 DoD,顺序不能反。
- **`commit-gate`**:动手**后**的闸门 3。前者防越界扩 scope,后者防自作主张 commit。前后呼应。
- **`review`**:scope 对齐时如果涉及大破面变更,可同步触发它做 5 维度判据。

## Auto-invoke chain(conditional,不强 push)

完成本 skill 后,**按 task 性质分流**(不再 strict push):

- 有 test command DoD / 改公开 API / DoD 描述模糊 → invoke `acceptance`
- 文档型 task / feature.md AC 已细化到 command / 简单重构 → **直接进写代码**,跳过 acceptance
- 大功能 / 多方案纠结 / schema 改 / 跨 crate → 直接 invoke `design`(可选闸门 2.5)

判据见 `acceptance` 头部"何时必走 / 跳过"清单。
