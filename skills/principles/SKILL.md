# Principles

工程哲学的底座。多数日常工作不需要显式调用本 skill——它们已经融入其他 skill。**纠结时回到本 skill 找判据**。

---

## 触发场景

- 多种"看起来都行"的方案纠结
- 想做大决策(架构 / API / 重构)前需要哲学锚点
- 反思一个 design 是否过度复杂
- 写不下去的时候,需要重新校准取舍

**不触发**:具体 trigger 已经命中专项 skill 时(那时用专项的判据)。

---

## 4 条核心哲学(Linus / Unix 传统)

### 1. Good Taste — 消除特殊情况

> "有时你可以从不同角度看问题,重写它让特殊情况消失,变成正常情况。" — Linus

- 好品味是一种直觉,需要经验积累
- 消除边界情况永远优于增加条件判断
- 10 行带 if 判断 → 4 行无条件分支
- 空集合通过 `[ref, exp]` 退化成均匀分布,不需要单独 if

### 2. Never Break Consumer — 铁律

> "我们不破坏用户空间!" — Linus

- 任何导致现有调用方崩溃的改动都是 bug
- 向后兼容性是神圣不可侵犯的
- 库的职责是服务调用方,不是教育调用方

### 3. 实用主义 — 解决真实问题

> "我是个该死的实用主义者。" — Linus

- 解决实际问题,不是假想的威胁
- 拒绝"理论完美"但实际复杂的方案
- 代码要为现实服务,不是为论文服务

### 4. 简洁执念 — 复杂性是万恶之源

> "如果你需要超过 3 层缩进,你就已经完蛋了,应该修复你的程序。" — Linus

- 函数必须短小精悍,只做一件事并做好
- 命名简洁,不堆冗词
- 复杂性是万恶之源

## 元规则

### 一次只做一件事

专注当前任务。听指挥,先思考,聚焦。

### 三个关键问题

开始任何工作前先问:

1. **"这是个真问题还是臆想出来的?"** — 拒绝过度设计
2. **"有更简单的方法吗?"** — 永远寻找最简方案
3. **"会破坏什么吗?"** — 向后兼容是铁律

### 3 次尝试规则

每个问题最多尝试 3 次,然后停止。

遇到困难时:
1. **记录失败** — 你尝试了什么、具体错误、失败原因
2. **研究替代方案** — 找 2-3 个相似实现,注意不同方法
3. **质疑基本假设** — 这是正确的抽象层次吗?能否拆分?有更简单的方法吗?
4. **尝试不同角度** — 不同的库 / 框架?不同的架构?移除抽象而不是添加?

## 决策框架(多方案纠结时)

存在多个有效方法时,按以下优先级判断:

| 优先级 | 维度 | 一句话 |
|--------|------|--------|
| 1 | 可测试性 | 我能轻松测试这个吗? |
| 2 | 可读性 | 6 个月后有人能理解这个吗? |
| 3 | 一致性 | 这符合项目模式吗? |
| 4 | 简洁性 | 这是有效的最简单解决方案吗? |
| 5 | 可逆性 | 以后改变有多困难? |

**关键判断不是 "会不会错",而是 "错了改起来贵不贵"**——可逆性优先。

## 工具使用原则

### 先查,后改

- 改公开 API 前,先查所有调用点
- 用陌生 symbol 前,先查定义
- 不要靠"编译失败 → 修"的被动学习

### 结构化输出优先

- 能拿 JSON / 结构化错误就别解析彩色 stdout
- `command --message-format=json` > `command 2>&1 | tail`

### 识别占位代码

- 碰到明显的 TODO / dummy / placeholder,先问用户再动手
- 对 WIP 层做深度 review 是浪费
